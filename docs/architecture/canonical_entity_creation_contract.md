# Canonical Entity Creation Contract

**Status:** Slice 7E contract freeze with explicit open decisions  
**Scope:** Canonical Product/ProductVariant creation authority and ID assignment

## 1. Scope

This contract separates four boundaries:

```text
identity resolution
  -> entity creation
  -> ID assignment
  -> approval and snapshot eligibility
```

It does not create entities, generate IDs, persist a catalog, or implement
governance.

## 2. Ownership

Product Intelligence owns the canonical catalog authority boundary. Ingestion,
Observation Registry, Evidence Registry, candidate generation, and matching do
not create canonical Products or ProductVariants.

The repository contains no production creation service, repository, registry,
external catalog authority, or ID assignment component.

All existing `Product(...)` and `ProductVariant(...)` construction sites are
test fixtures used by Product Intelligence tests. They are not production
creation authorities.

## 3. Product Creation Authority

```text
OPEN — canonical Product creation authority is not currently defined.
```

Product Intelligence owns the eventual boundary, but no concrete service,
curated source, external catalog, or repository is authorized to create a
Product.

## 4. Variant Creation Authority

```text
OPEN — canonical ProductVariant creation authority is not currently defined.
```

Variant creation remains subordinate to governed Product identity. No existing
component creates or assigns canonical variants.

## 5. Canonical ID Authorities

The concrete authority for both identifiers is unresolved:

```text
OPEN — canonical_product_id assignment authority.
OPEN — canonical_variant_id assignment authority.
```

The existing models require externally supplied identifier fields, but that
requirement does not establish who supplies them.

## 6. Deterministic or External IDs

The repository establishes neither:

- deterministic IDs derived from identity attributes;
- externally assigned catalog IDs;
- IDs generated by a governed catalog service;
- another stable ID mechanism.

Therefore:

```text
OPEN — canonical ID strategy and stability mechanism.
```

No UUID, random value, hash, name-derived ID, observation ID, platform ID,
timestamp, storage path, worker ID, or runtime value may be used until this
decision is frozen.

## 7. Product Creation Preconditions

The following boundary is frozen:

- a `NormalizedObservation` is not by itself sufficient authority to create a
  Product;
- Product identity must be resolved before Product creation;
- creation and approval are distinct concepts;
- matching confidence does not authorize catalog creation by itself.

The exact required evidence, fields, authority, and approval state are:

```text
OPEN — Product creation preconditions.
```

## 8. Variant Creation Preconditions

The following boundary is frozen:

- Variant creation requires a governed parent Product relationship;
- Variant identity must not bypass Product identity resolution;
- quantity text, platform identifiers, and observation IDs do not authorize
  Variant creation by themselves.

Whether the parent Product must be approved, which Variant evidence is
required, and whether pending Variants are permitted are:

```text
OPEN — ProductVariant creation preconditions.
```

## 9. Identity, Creation, and Approval

These remain separate:

```text
identity resolution
  -> entity creation
  -> catalog approval
  -> CandidateCatalogSnapshot eligibility
```

`ReviewQueueManager` is Product Intelligence match review only and is not a
catalog creation or approval authority.

The repository does not define whether creation precedes approval, whether
pending entities receive IDs, or who performs approval:

```text
OPEN — creation/approval ordering and authority.
```

## 10. Replay and Idempotency

The following protections are frozen:

- replaying an observation must not silently create duplicate canonical
  entities;
- platform listing IDs and observation IDs must not become canonical IDs;
- capture timestamps, runtime metadata, worker IDs, and storage paths must not
  change canonical identity;
- repeated evidence must remain provenance.

Exact behavior for repeated creation requests, including return, no-op, or
conflict results, is:

```text
OPEN — creation idempotency and replay result semantics.
```

## 11. Conflict Behavior

No conflict policy exists for:

- an already-used canonical Product ID;
- an already-used canonical Variant ID;
- one identity mapping to multiple IDs;
- one ID receiving conflicting identity data;
- a Variant identity changing parent Product.

All are:

```text
OPEN — canonical entity creation conflict semantics.
```

No implementation may silently overwrite or merge canonical entities.

## 12. Provenance

Any future creation decision must preserve or reference:

- `observation_id`;
- `RawArtifactReference`;
- `EvidenceReference`;
- `ObservationFieldReference`;
- parser version;
- normalization version;
- platform identifiers;
- platform listing identity;
- assigned canonical Product/Variant identity.

The existing Evidence Registry remains the provenance authority. No second
evidence system is introduced.

## 13. Cross-Platform Creation

Canonical creation must remain platform-independent:

```text
Platform A observation + Platform B observation
  -> governed identity decision
  -> one canonical entity, if authorized
```

Platform A or B listing IDs must never become canonical Product or Variant IDs.
Cross-platform creation and convergence evidence remain governed Product
Intelligence decisions and are not implemented here.

## 14. Catalog Source

No authoritative catalog source exists in the repository. There is no
production repository, service, external source, seed catalog, or persistence
boundary for canonical entities.

```text
OPEN — authoritative catalog source and persistence boundary.
```

`CandidateCatalogSnapshot` remains a derived in-memory view and is not a source
of canonical entities.

## 15. Explicit Non-Goals

This contract does not implement or authorize:

- Product or ProductVariant creation;
- canonical ID generation;
- Product/Variant repositories or registries;
- catalog persistence;
- approval workflow;
- listing association;
- CandidateCatalogSnapshot population;
- candidate generation or matching;
- changes to ingestion or evidence registries.

## 16. Remaining Open Decisions

Before entity creation implementation, the following must be frozen:

1. Product creation authority.
2. Variant creation authority.
3. Canonical Product and Variant ID assignment authority.
4. Deterministic versus externally assigned ID strategy.
5. Product creation preconditions.
6. Variant creation preconditions.
7. Creation and approval ordering.
8. Creation replay/idempotency results.
9. Canonical ID and identity conflict behavior.
10. Authoritative catalog source and persistence lifecycle.

No implementation may resolve these by assumption.
